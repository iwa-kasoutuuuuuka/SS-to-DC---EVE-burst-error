# Dreamcast ホームブリュー知見まとめ（EVE-DC プロジェクト由来）

作成日: 2026-10-10
出所: `F:/DC_EVE`（セガサターン版『EVE burst error』を KallistiOS + DreamSDK / C 言語で Dreamcast に移植するプロジェクト）で実際に踏んだ問題と、その解決策。

- ここに書いてあるのは **このプロジェクトで実際に確認したこと** だけ。一般的なハード仕様は `skills/` 以下の汎用ガイドを参照。
- 動作確認はすべて **Flycast 2.6（Windows）** 上。**実機では未検証**（ROADMAP 6-4）。実機固有の挙動（GD-ROM ドライブのシーク、MIL-CD 起動、VMU の実物）は別途確認が必要。
- ゲーム固有のフォーマット（.SCO / .B1 / .CMP など）の詳細は `.claude/skills/` の各スキルにあり、ここでは「移植作業の進め方」として一般化できる部分だけを抜き出している。

## 1. 起動するディスクイメージを作る

### 1.1 手順（`make cdi` の中身）

```
sh-elf-objcopy -O binary main.elf 1ST_READ.BIN
scramble 1ST_READ.BIN iso_root/1ST_READ.BIN
mkisofs -V "EVE_DC" -G engine/IP.BIN -r -J -l -o build/eve_dc.iso iso_root
cdi4dc build/eve_dc.iso build/eve_dc.cdi -d
```

- **`1ST_READ.BIN` はスクランブル必須**。未スクランブルだと黒画面のまま起動しない。
- **IP.BIN の Boot Filename が `1ST_READ.BIN` と一致**していること。
- `mkisofs` の `-G IP.BIN` でブートセクタを埋め込む。`-l`（長いファイル名）を落とすとファイルが見つからなくなる。
- `iso_root/` に置いたものがそのまま実行時の `/cd/` になる。

### 1.2 巨大アセットを ISO から除外・差し替える

元データを全部 `iso_root/` に置くと（このプロジェクトでは音声だけで 21GB）ISO が作れない。`-m` で除外し、`-graft-points` で「載せる分だけを置いたステージング用ディレクトリ」を差し込む。

```
mkisofs ... -m audio -graft-points -o build/eve_dc.iso . audio/=../iso_stage/audio/
```

- **graft 指定は必ず `-o` より後ろ**に置く。
- 「スクリプトを解析して実際に参照されるファイルだけをステージする」ツールを用意すると、ディスク別ビルドと容量管理が楽になる（`stage_voices.py` / `stage_assets.py`）。
- graft で差し替える構成にすると、常に必要な共通ファイル（UI 素材など）を載せ忘れやすい。実際にメッセージ枠が表示されなくなった。共通ディレクトリは Makefile で常に graft する。

### 1.3 容量

- 80 分 CD-R の上限は **360,000 セクタ = 737MB（703MiB）**。判定は ISO のセクタ数で行う。
- **CDI ファイルは 2352 バイト/セクタで格納されるので、ISO 663MiB が CDI では約 758MB になる**。CDI のファイルサイズが 700MB を超えていても問題ない。
- 音声を 44.1kHz → 22.05kHz の ADX に再エンコードするとほぼ半分になる（135,000 → 67,536 バイト）。libADX は任意レートを再生できる。
- 余裕が少ないディスクは「BGM を 90 秒で打ち切る」など、調整弁を 1 つ決めておく。

### 1.4 壊れた CDI

- **`make cdi` を 2 つ同時に走らせると CDI が壊れる**（本来より短い 175MB 程度のファイルになり、Flycast が `Invalid CDI file` で落ちる）。複数のシェルやエージェントで作業するときは、開始前に `tasklist` で make / mkisofs / cdi4dc / flycast が動いていないことを確認する。

### 1.5 実機に焼くとき（手順のみ整備、未実施）

- DiscJuggler か ImgBurn、DAO/SAO、4〜8 倍の低速、700MB メディア。
- MIL-CD 対応の本体（2000 年 10 月以前の製造、または対応改造機）が必要。
- 実機にはシリアルログが無い。落ちたら画面のメッセージと操作手順を記録し、Flycast で同じ手順を再現して調べる。

## 2. ビルド環境（DreamSDK / Windows）の罠

- `make` は DreamSDK の環境変数（`DREAMSDK_HOME`, `KOS_BASE` など）を持つシェルでしか通らない。
  - Python の `subprocess` から呼ぶと kos-cc のヘルパーが環境を見つけられない。
  - login shell 経由にすると今度は `KOS_CFLAGS` が二重に渡り、リンカスクリプト重複でリンクに失敗する。
  - → ビルドは bash スクリプト、エミュレータ起動と集計は Python、と分離した。
- `kos-cc` を Makefile を通さず直接呼ぶと、**エラーも出さずに何もしない**ことがある。「エラーが無い＝成功」と誤認する。単体のコンパイル確認も `make foo.o` で行う。
- **引用符入りの `-D` は kos-cc ラッパーが壊す**。`-DSTART_SCRIPT_NAME=A001_6` のように識別子で渡し、C 側で `#` 演算子で文字列化する。
- **make は CFLAGS の変更を検知しない**。フラグを変えたら該当 .o を作り直す。
- **`-DNDEBUG` の .o とデバッグの .o が混ざる**と、触っていないファイルのログだけが出なくなり原因調査を誤る。リリースビルドの前後は必ず `make clean`。
- romdisk は `genromfs` → `bin2o` で ELF に埋め込まれるが、依存関係がディレクトリの中身を見ていない。中身を変えたら `romdisk.img` を作り直させる。
- `-Werror` ではないので、警告がそのまま実害（書式不一致など）になりやすい。警告は読む。
- MSYS の python は `/FI` のような引数を `C:/DreamSDK/FI` に変換する。`//FI` と書くとそのまま渡る（`MSYS2_ARG_CONV_EXCL` は効かなかった）。また `C:/...` 形式の絶対パスを壊すことがあるので `/c/...` 形式か相対パスで渡す。
- MSYS の python には PIL が無い。画像変換は Windows 側の `py -3` を使う。

## 3. PVR（描画）

### 3.1 初期化と基本方針

- 画面は `DM_640x480` / `PM_RGB565`。
- PVR の OPB は **OP（不透明）と TR（半透明）だけ**確保した（PT・modifier は使わない）。2D のアドベンチャーゲームならこれで足りる。
- VBlank 同期は `pvr_wait_ready()` に任せる。メインループに `thd_sleep` を入れない。
- ポリゴンヘッダは `static` にキャッシュし、テクスチャポインタが変わったときだけ `pvr_poly_compile` し直す。

### 3.2 砂嵐・市松模様になる原因（3 つとも踏んだ）

1. **VRAM への書き込み先アドレス**
   `sq_cpy` などで直接転送するとき、宛先がオフセット値のままだと化ける。PVR の物理空間を指す。
   ```c
   sq_cpy((void*)(0xa4000000 | (uintptr_t)vram_ptr), src, size);
   ```
2. **データ形式と描画フラグの不一致**
   RGB565 のデータを `PVR_TXRFMT_ARGB1555` で描くと、最上位ビットが透過フラグとして解釈され、形は見えるが黒く欠けたり色が反転したりする。
3. **長方形テクスチャの twiddle**
   512x256 のような非正方形テクスチャを twiddled として扱うと崩れる。

### 3.3 採用した解決策：線形（非 twiddle）＋ストライド

テクスチャは全部「512x256・非 twiddle・ストライド 512」に統一し、PC 側で線形バイナリに変換して `pvr_txr_load` で転送する。

```c
pvr_txr_set_stride(512);
pvr_poly_cxt_txr(&cxt, PVR_LIST_OP_POLY,
    PVR_TXRFMT_RGB565 | PVR_TXRFMT_NONTWIDDLED | PVR_TXRFMT_X32_STRIDE,
    512, 256, txr, PVR_FILTER_NONE);
```

- 背景は `RGB565`（OP リスト）、文字・UI・差分パーツは `ARGB4444`（TR リスト、SRCALPHA / INVSRCALPHA）。
- **`pvr_txr_set_stride()` はグローバルな状態**。libmpeg でムービーを再生したあとは設定し直す。
- 512x256 に収まらない素材は分割する（288x432 の UI シートを上下 216px ずつ 2 枚にした）。
- 大きいバッファは `memalign(32, ...)` で確保する（SQ / DMA 転送は 32 バイト境界が必要）。

### 3.4 独自テクスチャコンテナ

PVR ヘッダを解釈する代わりに、最小限の独自ヘッダを付けた線形データにした。ロード側は「512x256 テクスチャの左上にコピーする」だけになる。

```
"EVB1"  u16 幅  u16 高さ  u16 形式(0=RGB565, 1=ARGB4444)  u16 0   + 幅*高さ*2 バイト（LE、上から下）
```

### 3.5 Z 順とフェード

- 2D でも Z で重ね順を決める：背景 → 差分パーツ (z=3) → フェード用の黒ポリゴン (z=4) → メッセージ枠 (z=5) → 文字 (z=10)。
- **フェードの黒ポリゴンを最前面に置くと、フェードアウト直後に出すメニュー文字まで隠れる**（タイトルが真っ黒になった）。背景の上・メッセージ窓の下に置く。
- パレットアニメ（夜景のランプ点滅など）は、直接色テクスチャに変換してしまうと再現できない。白フラッシュで近似した。正確にやるならパレットテクスチャで持つ必要がある。

### 3.6 低解像度素材の拡大

- 元が 320x224 の画面は、640x480 に横 2.0 倍・縦 2.142 倍（バイリニア）で全面表示にした。CRT 上ではどちらも 4:3 全面なので原作と同じ見え方になる。
- ピクセル等倍を優先するなら整数 2 倍（640x448 + 上下 16px の帯）という選択肢もある。
- テクスチャ端のバイリニア滲みは、端が画面外や UI の下に隠れる配置なら問題にならない。

## 4. ファイルシステムと CD

- romdisk は `/rd/`、CD は `/cd/`。**romdisk には「CD 無しでも起動できる最小限」だけ**入れ、本体データは CD に置く（シナリオを CD に移して ELF が 3.3MB → 2.6MB）。
- **起動直後は CD がまだ読めないことがある**。最初のファイルが開けるまで最大 3 秒リトライする。
- 読み込みは `/cd/...` → 無ければ `/rd/...` のフォールバック順にしておくと、CD 無しの検証ができる。
- Flycast は `/cd/` の大文字小文字を区別しないが、実機は ISO9660 の制約を受ける。**ファイル名は大文字化して統一**した。
- 参照名と実ファイル名が微妙に違うデータがある（末尾 1 文字余分など）。「末尾 1 文字を落として再試行」のようなフォールバックをローダーに入れた。
- **ディスク交換**：各ディスクに `/cd/DISCn.ID` というマーカーを置き、交換待ち画面で 1 秒ごとに `cdrom_reinit()` → マーカーの存在確認、という方法で検出できた。交換を伴わない検証は、別ディスクのマーカーを同梱したビルドで行う。
- 小さい `fread` を CD に対して大量に行うと極端に遅い（後述の libADX の件）。**CD から読むものは数十 KB 単位でバッファリングする**。

## 5. サウンド（最も時間を使った領域）

### 5.1 AICA のハードウェアループは 64K サンプルまで

- `snd_sfx` はサンプルをサウンド RAM に置いて AICA にループさせるが、**AICA は 64K サンプル（22050Hz で約 3 秒）を超えるサンプルをループできない**。
- 長い WAV を `snd_sfx_load` して鳴らすと、約 20 秒後に SH4 例外で落ちた。
- → **BGM は `snd_stream` で流す**。`snd_sfx` は短い効果音専用。

### 5.2 BGM の実装方針

- AICA ADPCM（モノラル 22050Hz）の WAV を **丸ごとメイン RAM に読み込み**、独自の `snd_stream`（ADPCM）で供給してループさせる。再生中に CD を読まないので、音声ストリームと競合しない。
- KOS の `snd_stream` は 4 本まで。BGM と音声で別ストリームにすれば同時に鳴る。
- **BGM 用のポーリングスレッドは作らず、メインループから毎フレーム `bgm_update()` を呼ぶ**形にした。スレッド版は、曲の切替でメインスレッドが CD 読みや `thd_join` で止まっている間に音声が終わるとハングした。
- 曲の切替は「停止 → 32KB ずつ `thd_sleep(1)` を挟みながら読む → 開始」。一気に読むと他のストリームが飢える。
- RAM 常駐なので曲ごとに 0.6〜3.3MB のヒープを使う。メモリ使用量を観察するときは BGM の切替による増減を差し引く。

### 5.3 kos-ports の libADX（1.0.1）は長時間運用に耐えなかった

症状：`LibADX: Stopping` と出たまま `adx_stop()` が戻らない。音声の再生中にメインスレッドが CD から別のファイルを読むと必ず再現した（シナリオの連結直後など）。

原因は 3 層あった。

1. **CD への細かい fread**：元の実装は 32 サンプルごとに 18 バイトを `fread` する（約 1400 回/秒）。メインスレッドが別ファイルを読んでキャッシュが外れると 1 回 200〜800ms かかる。
2. **停止待ちに出口が無い**：デコーダがバッファ待ちのまま終了フラグを見ない。
3. **コールバック内での待ち**：ストリームのコールバックがデータの到着を待って空回りする。これが **KOS の `snd_stream_poll` が持つロック越しにメインスレッドまで止める**（BGM の poll を呼んだメインスレッドが巻き添えになる）。これが元凶だった。

対処（ライブラリをプロジェクトに取り込んで改変。`-lADX` はリンクしない）：

- デコーダスレッド内に **32KB の先読みバッファ**を入れる（`ftell` は自前のファイル位置で代替）。
- **コールバックは絶対に待たない**。デコーダ → ロックフリーのリングバッファ（128KB）→ コールバック、とし、コールバックは手持ち分だけ返して残りを無音で埋める。
- デコーダは終了前にリングが空になるまで待つ（そうしないと台詞の語尾が切れる）。
- `adx_stop()` にタイムアウトを入れ、戻らなければ強制終了する。
- **世代カウンタ**を導入する。再生開始と強制終了のたびに増やし、取り残されたデコーダスレッドは「自分の世代ではない」と気づいたら自分のバッファを解放して黙って終了する（新しい再生のドライバには触らない）。
- ストリームを BGM と共有しているので、ライブラリ側で `snd_stream_shutdown()` を呼ばせない。

効果（同じ 150 秒のランダム走行）：強制終了 3 回 → 0 回、音声 31 本すべて正常終了。

その他の libADX の癖：

- `adx_dec()` はデコーダスレッドが生きていると `Already Running` で失敗する。`adx_stop()` は STREAMING 状態でしか効かない。→ 「stop → 10ms 間隔で最大 30 回 dec を再試行」。
- ファイルが無くても printf して 0 を返すだけ。事前に `fopen` で存在確認する。

### 5.4 一般化できる教訓

- **オーディオコールバックの中でブロックしない。** 足りなければ無音で埋めて返す。
- **ストリーミング再生中に、同じ CD から別の大きなファイルを一気に読まない。** 小分けにして間に sleep を挟むか、再生側に十分な先読みを持たせる。
- スレッドを止める処理には必ずタイムアウトと「取り残された側の後始末」を用意する。
- kos-ports のライブラリは、問題が出たらソースを取り込んで直すのが早い。

### 5.5 ムービー再生後のサウンド

libmpeg がサウンドハードウェアを使うため、ムービーの前に BGM と音声を止め、**再生後にサウンドドライバを初期化し直す**。これをしないと、次の音声で `Fatal: SH4 exception when blocked` になるか音が出ない。

```
snd_stream_shutdown → snd_shutdown → snd_init → snd_stream_init
```

## 6. ムービー（libmpeg）

- libmpeg が再生できる形式に合わせて PC 側で変換する：**MPEG-1 PS、320x240、30fps、約 742kbps、音声は MP2 モノラル 32kHz**（ffmpeg）。
- 再生の流れ：`snd_stream_init()` → `mpeg_player_create` → `mpeg_play(中断ボタン)` → destroy → サウンド再初期化（5.5）→ `pvr_txr_set_stride(512)` の再設定。
- libmpeg は `pvr_init` / `vid_set_mode` を呼ばないので、PVR 自体の再初期化は不要だった。
- 再生はブロッキング。中断ボタン（A / Start）を渡しておく。
- 元が 320x160 のムービーは、上詰めで 320x224 に置いてから 320x240 に引き伸ばし、ゲーム中の背景と同じ位置に映るようにした。
- 切り分け用に、ムービーを丸ごとスキップするビルドフラグ（`-DNO_VIDEO`）を残しておくと、音の問題との切り分けが速い。

## 7. 日本語テキスト

- **BIOS フォントで Shift-JIS がそのまま描ける**：`bfont_set_encoding(BFONT_CODE_SJIS)`。24px 高、全角 24px 幅、半角 12px 幅。独自フォントが解析できるまでの間、これで開発を進められた。
- 文字は毎フレーム描かず、**512x256 ARGB4444 のテクスチャに文字列を描き込み、内容が変わったときだけ更新**して TR リストで 1 枚貼る。
- Shift-JIS は `uint8_t*` で扱い、先頭バイト 0x81–0x9F / 0xE0–0xFC を 2 バイト文字として処理する。文字化けの原因はほぼ 2 バイト境界のずれ。
- 行頭禁則（、。」！？ など）は 1 文字ぶら下げで処理した。
- 独自フォントを使う場合：グリフ（16x16・4bpp）を RAM に置き、コード表を二分探索して引く。4bit の輝度を ARGB4444 のアルファに入れ、色は文字色を使うと、任意色のアンチエイリアス文字になる。収録されていない字と半角は BIOS フォントにフォールバックする。
- 1 文字ごとのデバッグ printf は極端に遅い。専用フラグ（`-DTEXT_DEBUG_DUMP`）のときだけ出す。

## 8. 入力と VMU

- `maple_enum_type()` の戻り値は必ず NULL チェックする。コントローラ未接続・初期化完了前のアクセスでクラッシュする。
- VMU セーブは `vmu_pkg_build` + `vmufs_write`。約 8.3KB のデータ（スクリプト名、実行位置、背景名、変数 4096 個、BGM 番号）を 3 スロットに保存できた。
- **セーブデータにはバージョン番号を入れる**。項目を追加したら旧バージョンは「データなし」として扱う。
- VMU は小さい。既読フラグ（512KB のビットマップ）は保存を諦め、セッション内の RAM だけで持った。
- Flycast は既定で VMU が 2 枚刺さっている。**前回の実行で残ったセーブを自動テストが「ロード」して、まったく別の場面へ飛ぶ**ことがある。

## 9. メモリと長時間安定性

- メインループから一定フレームごとにヒープ使用量をシリアルへ出し（`MEM: used/free`）、長時間の自動走行で傾きを見る。この方法で 1 件のリークを特定した。
  - 原因：コンテキスト初期化関数が `memset` の前に旧バッファを `free` していなかった（ロードやタイトル復帰のたびに 50〜70KB）。
  - **「初期化関数が再初期化にも使われる」箇所は要注意。**
  - 30 分走行でヒープが 4.97MB → 8.90MB、空きが 44KB まで減って進行が極端に遅くなった。修正後は 10 分で 3.52 → 3.57MB と平坦。
- リークを探すときは、まず「正当に増減するもの」（RAM 常駐の BGM など）を差し引く。
- 短時間のテストでは見つからない。10 分・30 分単位の自動走行が必要。

## 10. デバッグとテスト自動化（Flycast）

### 10.1 シリアル出力

- デバッグの主手段は `printf` → Flycast の「Flycast Serial Output」ウィンドウ。
- **Python の `Popen` で Flycast を起動するとシリアル窓が出ない**。PowerShell の `Start-Process` で起動し、PID で追う。
- シリアル窓の内容は、そのコンソールにアタッチして `CONOUT$` を直接開き、1 行ずつ読むと取得できる（標準出力がパイプのときは `GetConsoleScreenBufferInfo` が失敗する。一括読みも失敗する）。PowerShell 5.1 では `0xC0000000` が負の Int32 になるので `[uint32]3221225472` と書く。
- **シリアル出力は遅く、ゲームの速度を律速する**。1 行ごとにログを出すデバッグビルドは、自動送りが約 3 行/秒・十数 fps に頭打ちになる（フレーム数で指定したタイマーが実時間で数倍に延びる）。長時間走行用にログを切り詰めるフラグを用意する。
- デバッグ出力は `#ifndef NDEBUG` で囲む。エラー報告（ファイルが無い等）だけは無条件で残す。

### 10.2 無人テスト用のビルドフラグ

エンジン側に入力注入を仕込んでおくと、エミュレータを外から操作しなくても回帰テストができる。

| フラグ | 動作 |
|---|---|
| `-DDEMO_AUTO_ADVANCE=N` | N フレームごとに決定ボタンを自動入力 |
| `-DDEMO_RANDOM=seed` | 選択肢を擬似乱数で選ぶ |
| `-DDEMO_EXPLORE` | 未選択の項目を優先し、セーブ／ロードを避ける |
| `-DDEMO_KEYS=N` | システムメニューなどのキーを周期的に注入 |
| `-DSTART_SCRIPT_NAME=X` / `-DSTART_BLOCK=id` | 任意の場面から起動 |
| `-DNO_VIDEO` / `-DNO_INTRO` | ムービーを飛ばす |
| `-DMEM_LOG_FRAMES=N` | ヒープ使用量の出力間隔 |

- 「ビルド → CDI → Flycast 起動 → 一定時間シリアル採取 → 集計（到達した場面、欠落ファイル、未知の命令、範囲外アクセス、ヒープ推移）」を 1 コマンドにしておくと、以後の全作業の回帰テスト基盤になる。
- ランダム選択だけでは物語が進まない（拠点のメニューを回り続ける）。カバレッジを上げるには探索モードか、各場面を直接起動する単体走行が要る。
- スクリーンショットは全画面キャプチャなので、Flycast のウィンドウを決まった位置・サイズに移動して最前面にしてから撮る。
- **Flycast が最前面になった瞬間、ユーザーのキー入力やゲームパッドがゲームに流れ込む**。「勝手に進む」ときは、まず入力ログで実入力かどうかを確認する。

### 10.3 報告の仕方

「どの段階のログまで出たか」と「画面に何が映ったか」を分けて記録する。起動確認の目印になるログ行（romdisk マウント、CD 準備完了、背景ロード成功、最初のテキスト描画）を決めておく。

## 11. サターン → Dreamcast 移植で分かったこと

### 11.1 元データの抽出が最大の罠

- **旧抽出スクリプトが「ファイルサイズ分の生セクタ」をコピーしていた**ため、2352 バイトごとに 304 バイトの同期・EDC/ECC が混入し、末尾の約 13% が欠落していた。
- これに気づかないまま解析を続け、「ノイズだらけの画像」「途中で壊れるスクリプト」「0 バイトのムービー」「再生時間が短すぎる音声」をフォーマットの謎だと誤解して時間を失った（シナリオと画像で 2 回踏んだ）。
- **解析がうまくいかないときは、フォーマットを疑う前に抽出を疑う。** ディスクイメージから 2048 バイトのユーザーデータだけを取り出して再抽出する。
- 派生物（過去に変換した PNG、ADX、MPG など）は信用せず、原本から作り直す。

### 11.2 フォーマット解析の進め方

- **全ファイルに対する検証スクリプト**を作る（命令境界と参照先が 100% 一致するか、画像のストリームを過不足なく消費するか）。1 ファイルで動いても、全体で検証すると誤解が見つかる（画像ヘッダの読み違いは、585 枚中 246 枚でだけ化けていた）。
- **別機種版との差分が決定的な手がかりになる**。Windows 版のスクリプトがサターン版と命令単位でほぼ同一で、1 つの命令だけが置き換わっていたことから、不明だった命令が「BGM 再生」だと確定した。
- 「純粋な RLE」のように単純に見える圧縮でも、未解明のビットが残っていたら疑う（ランの下位バイトは「左をコピー／上をコピー」を選ぶマスクだった）。
- 暗号化を疑う前に、標準形式として読めるか試す（ADX は暗号化されておらず、vgmstream でそのまま変換できた）。

### 11.3 アセットの移し替え

| サターン側 | Dreamcast 側 | メモ |
|---|---|---|
| 15bit 色（`1 BBBBB GGGGG RRRRR`）の独自圧縮画像 | RGB565 / ARGB4444 の線形テクスチャ | PC で事前変換。透過色（0xFFFF）はアルファに |
| 320x224 画面 | 640x480 | 3.6 参照 |
| Cinepak ムービー（Sega FILM, .CPK） | MPEG-1（libmpeg） | ffmpeg で変換 |
| SCSP シーケンス BGM（.SEQ + 音色バンク） | AICA ADPCM のストリーム | **PC で鳴らす手段が無い**。Windows 版の MIDI を SoundFont でレンダリングして代用（tinysoundfont + GM サウンドフォント、ffmpeg の `adpcm_yamaha`） |
| 音声 | CRI ADX（libADX） | 22.05kHz 化で容量半減 |
| 独自ビットマップフォント | RAM 上のグリフ表＋テクスチャ描画 | 解析できるまでは BIOS フォント |
| VDP2 のパレットアニメ | （直接色では再現不可） | 近似で妥協 |
| バックアップ RAM | VMU | 容量が小さい |

- 立ち絵が「背景に焼き込まれた別画像」として収録されていて、表情だけが小さな差分パッチ、という構成だった。**「立ち絵を表示する命令」が見つからないときは、データの持ち方が想像と違う可能性を考える。**
- 元のゲームのディスク構成（どの音声がどのディスクにあるか）を調べると、そのまま移植版のディスク分割案になる。

## 12. 症状別の早見表

| 症状 | まず疑うこと |
|---|---|
| 黒画面で起動しない | スクランブル漏れ／IP.BIN の Boot Filename／`vid_set_mode` を呼んでいるか |
| 砂嵐・市松模様 | VRAM 宛先アドレス／RGB565 と ARGB1555 の取り違え／twiddle 指定（`NONTWIDDLED` と `X32_STRIDE` を付け、`pvr_txr_set_stride` を呼ぶ） |
| 形は見えるが色が反転・欠ける | テクスチャ形式フラグの不一致 |
| ムービー後に画面が崩れる | `pvr_txr_set_stride()` の再設定 |
| 背景は出るが文字が出ない | TR リストに submit しているか／`bfont_set_encoding(BFONT_CODE_SJIS)`／文字テクスチャ確保後に描いているか |
| フェード後に文字が出ない | フェード用ポリゴンの Z が文字より手前 |
| 文字化け | Shift-JIS の 2 バイト境界ずれ |
| CD のファイルが開けない | `iso_root/` に無い／mkisofs の `-l`／大文字小文字／起動直後で CD 未準備 |
| コントローラが効かない | `maple_enum_type` の NULL／エミュレータ側のポート割り当て |
| 起動してすぐリブート | スクリプト実行が範囲外で終了扱い → 自動入力で再起動、の連鎖 |
| `LibADX: Stopping` の後に固まる | 5.3（kos-ports 版 libADX を使わない） |
| ムービー後に音が出ない／次の音声で落ちる | サウンドドライバの再初期化（5.5） |
| BGM が約 20 秒後に SH4 例外 | AICA の 64K サンプル制限。`snd_sfx` ではなく `snd_stream` |
| 曲の切替でハング | BGM をスレッドで回している／一気読みで他ストリームが飢える |
| 時間とともに重くなる | ヒープリーク。`MEM:` ログで傾きを見る |
| 一部のログだけ出ない | NDEBUG の .o が混ざっている → `make clean` |
| Flycast が `Invalid CDI file` | `make cdi` の同時実行で CDI が壊れた |
| セーブできない | VMU が刺さっているか |

## 13. まだ分かっていないこと

- **実機での動作全般**（MIL-CD 起動、CD-R の読み取り速度下での音声・BGM の安定性、物理的なディスク交換の検出、VMU の実物）。libADX の飢餓問題は実機のシーク時間でさらに厳しくなる可能性がある。
- ムービーの AV 同期（Flycast で最後まで再生されることは確認、音ずれの体感評価は未実施）。
- BGM の正確なループ点。
- パレットアニメの正確な再現方法。
