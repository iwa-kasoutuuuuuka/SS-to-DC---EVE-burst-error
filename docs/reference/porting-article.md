サターンのADVをDreamcastに移植して分かった、ホームブリュー開発の落とし穴まとめ

セガサターン版『EVE burst error』を、Dreamcast で動く自作エンジンに載せ替えるプロジェクトを個人で進めています。開発環境は KallistiOS（KOS）+ DreamSDK、言語は C です。

台詞・選択肢・背景・表情差分・音声・BGM・ムービー・セーブ／ロードまで動くようになったので、ここまでに踏んだ落とし穴と解決策を全部書き残します。Dreamcast のホームブリュー情報は英語圏に偏っていて、日本語でまとまった「実際にハマった記録」は少ないので、同じことをやる人の時間が少しでも節約できれば嬉しいです。

最初にお断りです。

- 動作確認はすべてエミュレータ（Flycast 2.6、Windows）上です。実機ではまだ動かしていません。実機固有の話（GD-ROM ドライブのシーク、MIL-CD 起動、VMU の実物）は未検証です
- 書いてあるのは、このプロジェクトで実際に確認したことだけです。ハードウェア仕様の網羅的な解説ではありません
- ゲームのデータは自分で所有しているディスクから抽出したもので、配布はしていません。この記事にもデータやその復元手順そのものは載せず、開発上の知見だけを書きます

長いので、目次から必要なところだけ読んでください。

## 1. 起動するディスクイメージを作る

### 手順

ビルドした ELF から CDI を作る流れは次の 4 ステップです。Makefile の make cdi にまとめています。

```
sh-elf-objcopy -O binary main.elf 1ST_READ.BIN
scramble 1ST_READ.BIN iso_root/1ST_READ.BIN
mkisofs -V "EVE_DC" -G engine/IP.BIN -r -J -l -o build/eve_dc.iso iso_root
cdi4dc build/eve_dc.iso build/eve_dc.cdi -d
```

ここでのポイントです。

- 1ST_READ.BIN はスクランブル必須です。未スクランブルだと黒画面のまま起動しません
- IP.BIN の中の Boot Filename が 1ST_READ.BIN と一致している必要があります
- mkisofs の -G でブートセクタ（IP.BIN）を埋め込みます
- -l（長いファイル名）を落とすと、実行時にファイルが見つからなくなります
- iso_root に置いたものが、そのまま実行時の /cd/ になります

### 巨大アセットは ISO から除外して差し込む

元データを全部 iso_root に置くと ISO が作れません。このプロジェクトでは音声だけで 21GB ありました。そこで -m で除外し、-graft-points で「載せる分だけを置いたステージング用ディレクトリ」を差し込みます。

```
mkisofs ... -m audio -graft-points -o build/eve_dc.iso . audio/=../iso_stage/audio/
```

- graft の指定は必ず -o より後ろに置きます。前に置くと通りません
- 「シナリオスクリプトを解析して、実際に参照されるファイルだけをステージする」ツールを作っておくと、ディスク別ビルドと容量管理がとても楽になります
- graft で差し替える構成にすると、常に必要な共通ファイル（UI 素材など）を載せ忘れやすくなります。実際にメッセージ枠が表示されなくなりました。共通ディレクトリは Makefile で常に graft するようにしました

### 容量の考え方

- 80 分 CD-R の上限は 360,000 セクタ = 737MB（703MiB）です。判定は ISO のセクタ数で行います
- CDI ファイルは 1 セクタ 2352 バイトで格納されるので、ISO が 663MiB でも CDI は約 758MB になります。CDI のファイルサイズが 700MB を超えていても問題ありません。これを知らずに一度焦りました
- 音声を 44.1kHz から 22.05kHz の ADX に再エンコードすると、ほぼ半分になります（1 ファイルで 135,000 バイト → 67,536 バイト）。libADX は任意のサンプルレートを再生できます
- 余裕が少ないディスクは「BGM を 90 秒で打ち切る」のような調整弁を 1 つ決めておくと安心です

最終的に、原作と同じ 3 枚構成で、3 枚とも 80 分 CD-R に収まる見込みが立ちました（663.4MiB / 631.0MiB / 694.8MiB）。

### CDI が壊れる

make cdi を 2 つ同時に走らせると CDI が壊れます。本来より短い 175MB 程度のファイルになり、Flycast が Invalid CDI file で落ちます。複数のターミナルで作業しているときは、開始前に make / mkisofs / cdi4dc / flycast が動いていないことを確認します。

### 実機に焼くとき（手順を調べただけで未実施）

- DiscJuggler か ImgBurn で、DAO/SAO、4〜8 倍の低速、700MB メディア
- MIL-CD 対応の本体（2000 年 10 月以前の製造、または対応改造機）が必要
- 実機にはシリアルログがありません。落ちたら画面のメッセージと操作手順を記録して、エミュレータで同じ手順を再現して調べることになります

## 2. ビルド環境（DreamSDK / Windows）の罠

ここは地味ですが、合計するとかなり時間を取られました。

- make は DreamSDK の環境変数（DREAMSDK_HOME、KOS_BASE など）を持つシェルでしか通りません
- Python の subprocess から make を呼ぶと、kos-cc のヘルパーが環境を見つけられません
- それならと login shell 経由にすると、今度は KOS_CFLAGS が二重に渡り、リンカスクリプトの重複でリンクに失敗します
- 結局「ビルドは bash スクリプト、エミュレータ起動とログ集計は Python」と分離しました
- kos-cc を Makefile を通さずに直接呼ぶと、エラーも出さずに何もしないことがあります。「エラーが無い＝成功」と誤認します。単体のコンパイル確認も make foo.o のように Makefile 経由で行います
- 引用符入りの -D は kos-cc ラッパーが壊します。-DSTART_SCRIPT_NAME=A001_6 のように識別子で渡し、C 側でプリプロセッサの # 演算子を使って文字列化します
- make は CFLAGS の変更を検知しません。フラグを変えたら該当するオブジェクトファイルを作り直します
- -DNDEBUG でビルドしたオブジェクトとデバッグ用のオブジェクトが混ざると、「触っていないファイルのログだけが出ない」という状態になり、原因調査を誤ります。リリースビルドの前後は必ず make clean します
- romdisk は genromfs → bin2o で ELF に埋め込まれますが、依存関係がディレクトリの中身を見ていません。中身を変えたら romdisk.img を作り直させます
- -Werror ではないので、警告がそのまま実害（printf の書式不一致など）になりがちです。警告は読みます
- MSYS の python は /FI のような引数を C:/DreamSDK/FI に勝手に変換します。//FI と書くとそのまま渡ります（MSYS2_ARG_CONV_EXCL は効きませんでした）
- MSYS の python には PIL が入っていません。画像変換は Windows 側の Python を使います

## 3. PVR（描画）

### 基本方針

- 画面モードは DM_640x480 / PM_RGB565
- PVR のリストは OP（不透明）と TR（半透明）だけ確保しました。PT やモディファイアは使いません。2D のアドベンチャーゲームならこれで足ります
- VBlank 同期は pvr_wait_ready() に任せます。メインループに thd_sleep は入れません
- ポリゴンヘッダは static にキャッシュして、テクスチャが変わったときだけ pvr_poly_compile し直します

### 砂嵐・市松模様になる 3 つの原因

画面がランダムなノイズや市松模様になる現象に、3 回、別々の原因で遭遇しました。

1 つ目は、VRAM への書き込み先アドレスです。sq_cpy などで直接転送するとき、宛先がオフセット値のままだと化けます。PVR の物理空間を指すようにします。

```c
sq_cpy((void*)(0xa4000000 | (uintptr_t)vram_ptr), src, size);
```

2 つ目は、データ形式と描画フラグの不一致です。RGB565 のデータを PVR_TXRFMT_ARGB1555 として描くと、最上位ビットが透過フラグとして解釈され、「形は見えるが黒く欠ける、色が毒々しく反転する」という絵になります。

3 つ目は、長方形テクスチャの twiddle です。512x256 のような非正方形テクスチャを twiddled として扱うと崩れます。

### 解決策：線形（非 twiddle）+ ストライド

テクスチャはすべて「512x256・非 twiddle・ストライド 512」に統一しました。PC 側であらかじめ線形のバイナリに変換しておき、pvr_txr_load で転送します。

```c
pvr_txr_set_stride(512);
pvr_poly_cxt_txr(&cxt, PVR_LIST_OP_POLY,
    PVR_TXRFMT_RGB565 | PVR_TXRFMT_NONTWIDDLED | PVR_TXRFMT_X32_STRIDE,
    512, 256, txr, PVR_FILTER_NONE);
```

- 背景は RGB565 で OP リスト、文字・UI・差分パーツは ARGB4444 で TR リスト（SRCALPHA / INVSRCALPHA）
- pvr_txr_set_stride() はグローバルな状態です。libmpeg でムービーを再生したあとは設定し直す必要があります
- 512x256 に収まらない素材は分割します（288x432 の UI シートを上下 216px ずつ 2 枚にしました）
- 大きいバッファは memalign(32, ...) で確保します。SQ や DMA の転送は 32 バイト境界が必要です

### 独自のテクスチャコンテナ

PVR ファイルのヘッダを解釈する代わりに、最小限のヘッダを付けた線形データを自分で定義しました。ロード側は「512x256 テクスチャの左上にコピーするだけ」になり、バグの入る余地が減ります。

```
"EVB1"  u16 幅  u16 高さ  u16 形式(0=RGB565, 1=ARGB4444)  u16 0
続けて 幅 x 高さ x 2 バイト（リトルエンディアン、上から下）
```

### Z 順とフェード

2D でも Z で重ね順を決めます。このプロジェクトでは次の順です。

- 背景
- 差分パーツ（z=3）
- フェード用の黒ポリゴン（z=4）
- メッセージ枠（z=5）
- 文字（z=10）

フェード用の黒ポリゴンを最前面に置くと、フェードアウト直後に出すメニュー文字まで隠れます。タイトル画面が真っ黒になって悩みました。背景の上・メッセージ窓の下に置くのが正解でした。

また、パレットアニメ（夜景のランプの点滅など）は、画像を直接色のテクスチャに変換してしまうと再現できません。今は白フラッシュで近似しています。正確にやるならパレットテクスチャで持つ必要があります。

### 低解像度素材の拡大

- サターンの 320x224 画面は、640x480 に横 2.0 倍・縦 2.142 倍（バイリニア）で全面表示にしました。ブラウン管ではどちらも 4:3 全面に映るので、原作と同じ見え方になります
- ピクセル等倍を優先するなら、整数 2 倍（640x448 + 上下 16px の帯）という選択肢もあります
- テクスチャ端のバイリニアの滲みは、端が画面外や UI の下に隠れる配置なら問題になりません

## 4. ファイルシステムと CD

- romdisk は /rd/、CD は /cd/ にマウントされます。romdisk には「CD 無しでも起動できる最小限」だけを入れ、本体データは CD に置きます。シナリオを CD に移したら ELF が 3.3MB から 2.6MB になりました
- 起動直後は CD がまだ読めないことがあります。最初のファイルが開けるまで最大 3 秒リトライするようにしました
- 読み込みを「/cd/ → 無ければ /rd/」の順にしておくと、CD 無しの検証ができます
- Flycast は /cd/ 以下の大文字小文字を区別しませんが、実機は ISO9660 の制約を受けます。ファイル名は大文字に統一しました
- スクリプトが参照する名前と実ファイル名が微妙に違うデータがありました（末尾に 1 文字余分、など）。「末尾 1 文字を落として再試行」というフォールバックをローダーに入れています
- ディスク交換の検出は、各ディスクに DISC1.ID のようなマーカーファイルを置き、交換待ち画面で 1 秒ごとに cdrom_reinit() を呼んでマーカーの存在を確認する方法で動きました。物理的な交換を伴わない検証は、別ディスクのマーカーを同梱したビルドで行います
- 小さい fread を CD に対して大量に行うと極端に遅くなります（次の章の libADX の話です）。CD から読むものは数十 KB 単位でバッファリングします

## 5. サウンド（いちばん時間を使った領域）

### AICA のハードウェアループは 64K サンプルまで

snd_sfx はサンプルをサウンド RAM に置いて AICA にループ再生させる仕組みですが、AICA は 64K サンプル（22050Hz で約 3 秒）を超えるサンプルをループできません。

これを知らずに、長い WAV を snd_sfx_load して BGM として鳴らしたところ、約 20 秒後に SH4 例外で落ちました。

BGM は snd_stream で流す、snd_sfx は短い効果音専用、と覚えておけば大丈夫です。

### BGM の実装方針

- AICA ADPCM（モノラル 22050Hz）の WAV を丸ごとメイン RAM に読み込み、専用の snd_stream（ADPCM）で供給してループさせます。再生中に CD を読まないので、音声のストリーミングと競合しません
- KOS の snd_stream は 4 本まで使えます。BGM と音声を別のストリームにすれば同時に鳴ります
- BGM 用のポーリングスレッドは作らず、メインループから毎フレーム更新関数を呼ぶ形にしました。スレッド版は、曲の切替でメインスレッドが CD 読みや thd_join で止まっている間に音声の再生が終わるとハングしました
- 曲の切替は「停止 → 32KB ずつ thd_sleep(1) を挟みながら読む → 開始」です。一気に読むと他のストリームが飢えます
- RAM 常駐なので、曲ごとに 0.6〜3.3MB のヒープを使います。メモリ使用量を観察するときは、BGM の切替による増減を差し引いて見ます

### kos-ports の libADX は長時間運用に耐えなかった

台詞の音声は CRI ADX で、kos-ports の libADX（1.0.1）で再生していました。ところが、LibADX: Stopping とログに出たまま adx_stop() が戻ってこない、という現象が頻発しました。音声の再生中にメインスレッドが CD から別のファイルを読むと必ず再現します。

調べると原因は 3 層ありました。

1 層目は、CD への細かい fread です。元の実装は 32 サンプルごとに 18 バイトを fread します（1 秒に約 1400 回）。メインスレッドが別のファイルを読んでキャッシュが外れると、1 回の fread に 200〜800 ミリ秒かかっていました。

2 層目は、停止待ちに出口が無いことです。デコーダがバッファ待ちのまま、終了フラグを見ていませんでした。

3 層目が元凶で、コールバック内での待ちです。ストリームのコールバックが、データの到着を待って空回りしていました。これが KOS の snd_stream_poll が持つロック越しに、メインスレッドまで止めてしまいます。BGM のために poll を呼んだメインスレッドが巻き添えになるわけです。

対処として、ライブラリのソースをプロジェクトに取り込んで改変しました（kos-ports 版はリンクしません）。

- デコーダスレッドの中に 32KB の先読みバッファを入れる
- コールバックは絶対に待たない。デコーダ → ロックフリーのリングバッファ（128KB）→ コールバック、という構成にして、コールバックは手持ち分だけ返し、残りを無音で埋める
- デコーダは終了前にリングが空になるまで待つ（そうしないと台詞の語尾が切れます）
- adx_stop() にタイムアウトを入れ、戻らなければ強制終了する
- 世代カウンタを導入する。再生開始と強制終了のたびに増やし、取り残されたデコーダスレッドは「自分の世代ではない」と気づいたら、自分のバッファを解放して静かに終了する。新しい再生には触らない
- ストリームを BGM と共有しているので、ライブラリ側で snd_stream_shutdown() を呼ばせない

同じ 150 秒の自動走行で比べると、強制終了 3 回 → 0 回、音声 31 本すべてが正常終了になりました。

libADX にはほかにも癖があります。

- adx_dec() は、前のデコーダスレッドが生きていると Already Running で失敗します。adx_stop() は再生中の状態でしか効きません。「stop してから、10 ミリ秒間隔で最大 30 回 dec を再試行する」ようにしました
- ファイルが無くても printf して 0 を返すだけです。事前に fopen で存在確認します

### ここから得た教訓

- オーディオコールバックの中でブロックしない。足りなければ無音で埋めて返す
- ストリーミング再生中に、同じ CD から別の大きなファイルを一気に読まない。小分けにして間に sleep を挟むか、再生側に十分な先読みを持たせる
- スレッドを止める処理には、必ずタイムアウトと「取り残された側の後始末」を用意する
- kos-ports のライブラリで問題が出たら、ソースを取り込んで直すのが結局早い

### ムービー再生後のサウンド

libmpeg がサウンドハードウェアを使うので、ムービーの前に BGM と音声を止め、再生後にサウンドドライバを初期化し直します。これをしないと、次の音声で Fatal: SH4 exception when blocked になるか、音が出なくなります。

```
snd_stream_shutdown → snd_shutdown → snd_init → snd_stream_init
```

## 6. ムービー（libmpeg）

- libmpeg が再生できる形式に合わせて、PC 側で ffmpeg を使って変換します。MPEG-1 PS、320x240、30fps、約 742kbps、音声は MP2 モノラル 32kHz です
- 再生の流れは、snd_stream_init → mpeg_player_create → mpeg_play（中断ボタンを渡す）→ destroy → サウンド再初期化 → pvr_txr_set_stride(512) の再設定、です
- libmpeg は pvr_init や vid_set_mode を呼ばないので、PVR 自体の再初期化は不要でした
- 再生はブロッキングです。中断用のボタン（A と Start）を渡しておきます
- 元が 320x160 のムービーは、上詰めで 320x224 に置いてから 320x240 に引き伸ばし、ゲーム中の背景と同じ位置に映るようにしました
- ムービーを丸ごとスキップするビルドフラグを残しておくと、音まわりの不具合との切り分けが速くなります

## 7. 日本語テキスト

- BIOS フォントで Shift-JIS がそのまま描けます。bfont_set_encoding(BFONT_CODE_SJIS) を呼ぶだけです。高さ 24px、全角は幅 24px、半角は幅 12px。原作のフォントが解析できるまでの間、これで開発を進められたのは大きかったです
- 文字は毎フレーム描きません。512x256 の ARGB4444 テクスチャに文字列を描き込み、内容が変わったときだけ更新して、TR リストで 1 枚貼ります
- Shift-JIS は uint8_t の配列で扱い、先頭バイトが 0x81〜0x9F か 0xE0〜0xFC なら 2 バイト文字として処理します。文字化けの原因は、ほぼ 2 バイト境界のずれでした
- 行頭禁則（、。」！？など）は 1 文字ぶら下げで処理しています
- 原作フォントを使う場合は、グリフ（16x16、4bpp）を RAM に置き、文字コード表を二分探索して引きます。4bit の輝度を ARGB4444 のアルファに入れ、色は文字色を使うと、任意の色でアンチエイリアスの効いた文字になります。収録されていない字と半角は BIOS フォントにフォールバックします
- 1 文字ごとのデバッグ printf は極端に遅いです。専用のフラグを付けたときだけ出すようにしました

## 8. 入力と VMU

- maple_enum_type() の戻り値は必ず NULL チェックします。コントローラ未接続や、初期化完了前のアクセスでクラッシュします
- VMU へのセーブは vmu_pkg_build と vmufs_write で行います。約 8.3KB のデータ（スクリプト名、実行位置、背景名、変数 4096 個、BGM 番号）を 3 スロットに保存できました
- セーブデータにはバージョン番号を入れます。項目を追加したら、旧バージョンは「データなし」として扱います
- VMU は小さいです。既読フラグ（512KB のビットマップ）は保存を諦めて、起動中の RAM だけで持つことにしました
- Flycast は既定で VMU が 2 枚刺さっています。前回の実行で残ったセーブを自動テストが「ロード」してしまい、まったく別の場面へ飛ぶことがあります

## 9. メモリと長時間安定性

メインループから一定フレームごとにヒープ使用量をシリアルへ出力し、長時間の自動走行で傾きを見る、という方法でリークを 1 件見つけました。

- 30 分走らせるとヒープが 4.97MB から 8.90MB に増え、空きが 44KB まで減って、進行が極端に遅くなりました
- 原因は、コンテキストの初期化関数が memset の前に古いバッファを解放していなかったことです。ロードやタイトル復帰のたびに 50〜70KB ずつ漏れていました
- 修正後は 10 分で 3.52MB → 3.57MB と平坦になりました

教訓です。

- 「初期化関数が再初期化にも使われる」箇所は要注意です
- リークを探すときは、まず正当に増減するもの（RAM 常駐の BGM など）を差し引きます
- 短時間のテストでは見つかりません。10 分、30 分単位の自動走行が必要です

## 10. デバッグとテスト自動化（Flycast）

### シリアル出力

- デバッグの主な手段は、printf の出力を Flycast のシリアルコンソール窓で見ることです
- Python の Popen で Flycast を起動すると、シリアル窓が出ません。PowerShell の Start-Process で起動し、プロセス ID で追います
- シリアル窓の内容は、そのコンソールにアタッチして CONOUT$ を直接開き、1 行ずつ読むと取得できます。標準出力がパイプになっていると GetConsoleScreenBufferInfo が失敗し、一括読みも失敗しました
- シリアル出力は遅く、ゲームの進行速度を律速します。1 行ごとにログを出すデバッグビルドは、自動送りが約 3 行/秒、十数 fps で頭打ちになりました。フレーム数で指定したタイマーが、実時間では数倍に延びます。長時間走行用に、ログを切り詰めるフラグを用意しました
- デバッグ出力は #ifndef NDEBUG で囲みます。エラー報告（ファイルが無い、など）だけは無条件で残します

### 無人テスト用のビルドフラグ

エンジン側に入力の注入を仕込んでおくと、エミュレータを外から操作しなくても回帰テストができます。用意したのは次のようなフラグです。

- DEMO_AUTO_ADVANCE=N：N フレームごとに決定ボタンを自動入力する
- DEMO_RANDOM=seed：選択肢を擬似乱数で選ぶ
- DEMO_EXPLORE：まだ選んでいない項目を優先し、セーブ／ロードは避ける
- DEMO_KEYS=N：システムメニューなどのキーを周期的に注入する
- START_SCRIPT_NAME / START_BLOCK：任意の場面から起動する
- NO_VIDEO / NO_INTRO：ムービーを飛ばす
- MEM_LOG_FRAMES=N：ヒープ使用量の出力間隔

「ビルド → CDI 作成 → Flycast 起動 → 一定時間シリアルを採取 → 集計」を 1 コマンドにしておくと、以後のすべての作業の回帰テスト基盤になります。集計しているのは、到達した場面、欠落ファイル、未知の命令、範囲外アクセス、ヒープの推移です。

やってみて分かったこともあります。

- ランダム選択だけでは物語が進みません。拠点のメニューを回り続けます。カバレッジを上げるには、探索モードか、各場面を直接起動する単体走行が必要です
- スクリーンショットは全画面キャプチャなので、Flycast のウィンドウを決まった位置とサイズに移動して、最前面にしてから撮ります
- Flycast が最前面になった瞬間、自分のキー入力やゲームパッドの入力がゲームに流れ込みます。「台詞が勝手に進む」ときは、まず入力ログで実入力かどうかを確認します

### 記録の付け方

「どの段階のログまで出たか」と「画面に何が映ったか」を分けて記録します。起動確認の目印になるログ行（romdisk のマウント、CD の準備完了、背景ロードの成功、最初のテキスト描画）を決めておくと、切り分けが速くなります。

## 11. サターンから Dreamcast への移植で分かったこと

### 元データの抽出が最大の罠だった

振り返ると、いちばん時間を失ったのはここです。

以前作った抽出スクリプトが、ディスクイメージから「ファイルサイズ分の生セクタ」をそのままコピーしていました。生セクタは 2352 バイトで、ユーザーデータは 2048 バイトです。つまり 2352 バイトごとに 304 バイトの同期パターンや EDC/ECC が混入し、そのぶん末尾の約 13% が欠けたファイルになっていました。

これに気づかないまま解析を続け、「ノイズだらけの画像」「途中で壊れるスクリプト」「0 バイトのムービー」「再生時間が短すぎる音声」を、フォーマットの謎だと思い込んでいました。シナリオと画像で、同じ罠を 2 回踏んでいます。

- 解析がうまくいかないときは、フォーマットを疑う前に抽出を疑う
- ディスクイメージから 2048 バイトのユーザーデータだけを取り出して、抽出し直す
- 過去に変換した派生物（PNG、ADX、MPG など）は信用せず、原本から作り直す

### フォーマット解析の進め方

- 全ファイルに対する検証スクリプトを作ります。命令の境界と参照先が 100% 一致するか、画像のデータ列を過不足なく消費するか、といった検査です。1 ファイルで動いていても、全体で検証すると誤解が見つかります。画像ヘッダの読み違いは、585 枚中 246 枚でだけ絵が化けるという形で残っていました
- 別機種版との差分が決定的な手がかりになります。Windows 版のスクリプトがサターン版と命令単位でほぼ同一で、ある 1 つの命令だけが別の命令に置き換わっていたことから、意味が分からなかった命令が「BGM 再生」だと確定しました
- 単純な RLE に見える圧縮でも、意味の分からないビットが残っていたら疑います。ランの下位バイトは、「左のピクセルをコピーするか、1 行上のピクセルをコピーするか」を選ぶマスクでした。RLE だと思い込んでいる間は、絵に短い横筋が出ていました
- 暗号化を疑う前に、標準形式として読めるか試します。音声の ADX は暗号化されておらず、既存のツールでそのまま変換できました。鍵を探すスクリプトを書いた時間は無駄でした

### アセットの移し替え一覧

- 画像：サターンの 15bit 色の独自圧縮画像 → RGB565 / ARGB4444 の線形テクスチャ。PC で事前変換し、透過色はアルファにします
- 画面：320x224 → 640x480 に拡大
- ムービー：Cinepak（Sega FILM）→ MPEG-1。ffmpeg で変換して libmpeg で再生
- BGM：サターンのシーケンスデータ + 音色バンクは、PC で鳴らす手段がありませんでした。Windows 版に入っていた標準 MIDI をサウンドフォントでレンダリングし、AICA ADPCM のストリームにして代用しています
- 音声：CRI ADX のまま libADX で再生。22.05kHz 化で容量を半分に
- フォント：独自ビットマップフォント → RAM 上のグリフ表 + テクスチャ描画。解析できるまでは BIOS フォント
- パレットアニメ：直接色では再現できず、近似で妥協
- セーブ：バックアップ RAM → VMU。容量が小さい

もう 2 つ、データの持ち方について。

- 立ち絵は「人物を焼き込んだ背景の別バージョン」として収録されていて、表情だけが小さな差分パッチ、という構成でした。「立ち絵を表示する命令」をずっと探していましたが、そんな命令は存在しませんでした。命令が見つからないときは、データの持ち方が想像と違う可能性を考えたほうがいいです
- 元のゲームのディスク構成（どの音声がどのディスクに入っているか）を調べると、それがそのまま移植版のディスク分割案になりました

## 12. 症状別の早見表

最後に、症状から逆引きできるようにまとめておきます。

- 黒画面で起動しない → スクランブル漏れ、IP.BIN の Boot Filename、vid_set_mode を呼んでいるか
- 砂嵐・市松模様 → VRAM の宛先アドレス、RGB565 と ARGB1555 の取り違え、twiddle 指定（NONTWIDDLED と X32_STRIDE を付け、pvr_txr_set_stride を呼ぶ）
- 形は見えるが色が反転する・欠ける → テクスチャ形式フラグの不一致
- ムービー後に画面が崩れる → pvr_txr_set_stride の再設定
- 背景は出るが文字が出ない → TR リストに submit しているか、bfont_set_encoding を呼んだか、文字テクスチャの確保後に描いているか
- フェードのあと文字が出ない → フェード用ポリゴンの Z が文字より手前にある
- 文字化け → Shift-JIS の 2 バイト境界ずれ
- CD のファイルが開けない → iso_root に無い、mkisofs の -l、大文字小文字、起動直後で CD が未準備
- コントローラが効かない → maple_enum_type の NULL、エミュレータ側のポート割り当て
- 起動してすぐリブートする → スクリプトの実行が範囲外に出て終了扱いになり、自動入力で再起動している
- LibADX: Stopping のあと固まる → kos-ports 版 libADX を使わない（5 章）
- ムービー後に音が出ない、次の音声で落ちる → サウンドドライバの再初期化（5 章）
- BGM が約 20 秒後に SH4 例外 → AICA の 64K サンプル制限。snd_sfx ではなく snd_stream
- 曲の切替でハングする → BGM をスレッドで回している、一気読みで他のストリームが飢えている
- 時間とともに重くなる → ヒープリーク。使用量のログで傾きを見る
- 一部のログだけ出ない → NDEBUG のオブジェクトが混ざっている。make clean
- Flycast が Invalid CDI file → make cdi の同時実行で CDI が壊れた
- セーブできない → VMU が刺さっているか
